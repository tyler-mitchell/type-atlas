# Codex dynamic-tool host

## Objective

Identify the narrowest supported Codex integration that can expose the headless code-intelligence operations as task-bound dynamic tools. The host must preserve Codex-native patch items and avoid owning app-server transport or lifecycle when an official package already does so.

Target inspected: Codex Desktop `0.145.0-alpha.18` and its bundled `codex app-server` protocol on 2026-07-18.

## Established behavior

`thread/start` accepts a dynamic-tool namespace. The app server emits
`item/tool/call` requests and records completed calls as native
`dynamicToolCall` thread items. A dynamic result can contain input text or
images; it cannot produce a native `fileChange` item.

The installed app-server protocol generated by `codex app-server generate-ts` defines the call boundary as:

```ts
type ItemToolCallParams = {
  threadId: string;
  turnId: string;
  callId: string;
  namespace: string;
  tool: string;
  arguments: unknown;
};

type ItemToolCallResponse = {
  contentItems: Array<
    | { type: "inputText"; text: string }
    | { type: "inputImage"; imageUrl: string }
  >;
  success: boolean;
};
```

Direct use confirmed that a native Codex `fileChange` can be observed by a task-bound host and immediately followed by `code_intelligence.diagnostics({})`, with the workspace and changed file inferred from app-server task state.

## Current host

`packages/code-intelligence-codex/src/bridge.ts` owns the boundary the app-server
protocol assigns to its client: JSONL forwarding, namespace injection,
`item/tool/call` responses, and task-state capture.

Tool implementation modules are loaded through Vite's public server API. Vite
owns TypeScript transformation, dependency tracking, file observation, and
module invalidation. The bridge swaps the headless runtime after Vite observes
a loaded module change.

```ts
const vite = await createServer({
  root: packageRoot,
  server: { middlewareMode: true, watch: { usePolling: true } },
  appType: "custom",
})

const runtime = await vite.ssrLoadModule("/src/runtime.ts")

vite.watcher.on("all", (_event, file) => {
  if (vite.moduleGraph.getModulesByFile(file)?.size) {
    setImmediate(() => void reloadRuntime())
  }
})
```

Consequences:

- an implementation edit is active on the next turn without restarting Codex;
- a schema edit is active in a new task because `dynamicTools` is fixed by
  `thread/start`;
- there is no project-owned watcher, module cache, or renderer modification.

Polling is selected through Vite because Codex's patch operation can replace a
file atomically, and native filesystem watching exhausted the available file
handles in the production workspace. In one running native Codex task, changing
the implementation produced `vite-hmr-live` on the next call; restoring the
source then produced an empty result, both without rebuilding or restarting the
bridge.

Codex Desktop already honors `CODEX_CLI_PATH` when launching its app-server
binary. Pointing that supported launch override at the executable bridge keeps
the renderer unchanged and preserves the bundled Codex binary as the bridge's
upstream app-server process.

Status: native app-server task and same-process implementation reload observed.

The TypeScript Codex SDK does not currently provide that abstraction. `@openai/codex-sdk@0.145.0-alpha.24` implements `Thread` over `codex exec --experimental-json`; its public thread options contain no dynamic-tool namespace or server-request handler. The official app-server guide instead shows clients spawning `codex app-server`, framing JSONL messages, and handling the bidirectional stream directly.

The upstream Codex repository confirms that `dynamicTools` and `item/tool/call` are experimental app-server APIs and documents the client as the tool executor. It publishes version-specific generated TypeScript and JSON Schema, but no TypeScript app-server client package. An open upstream request for an `app-server-client` remains unresolved. This rules out the current TypeScript Codex SDK as a transport replacement, but not a generic JSON-RPC package or a desktop extension registration path.

The installed desktop renderer already owns dynamic-tool construction and dispatch. It handles `dynamic-tools-for-thread-start-requested` by constructing the `codex_app` namespace plus a built-in `plugin_management` namespace, and handles `dynamic-tool-call-requested` through an explicit namespace/tool switch before returning an `mcp-response` IPC message. Installed plugin metadata is not consulted as a general dynamic-tool provider; the only plugin-derived namespace in this path is the first-party plugin-management tool. No public plugin registration seam is present in this construction path.

Patching the minified renderer could bypass a protocol proxy, but would bind the integration to private desktop bundle symbols and still require a new renderer-to-Node execution boundary for the Volar runtime. That is less durable than the versioned app-server protocol and is not an acceptable open-source integration seam.
